# CLI reference

The canonical command is `metrora`.

When running from this repository before an official package exists, replace `metrora` with:

```bash
npm run dev --
```

For example, `metrora overview` becomes `npm run dev -- overview`.

Command help generated by the current source is authoritative:

```bash
metrora --help
metrora <command> --help
```

## Common filters

Most reporting and analytical commands accept some combination of:

- `--provider <provider>` — restrict results to one supported source;
- `--project <name>` — include matching projects; repeatable where documented;
- `--exclude <name>` — exclude matching projects; repeatable where documented;
- `--period today|week|30days|month|all|lifetime` — select a standard period;
- `--from YYYY-MM-DD --to YYYY-MM-DD` — use an exact date range;
- `--format <format>` — choose human-readable or machine-readable output.

A filter is accepted only when the command can apply it truthfully to the requested output.

## Usage and reporting

| Command | Purpose |
| --- | --- |
| `metrora` / `metrora report` | Interactive terminal usage dashboard. |
| `metrora today` | Dashboard or JSON output for today. |
| `metrora month` | Dashboard or JSON output for the current month. |
| `metrora overview` | Copy-pasteable plain-text overview. |
| `metrora status` | Compact today-and-month status, including machine-readable forms. |
| `metrora sessions` | Detailed per-session report, with optional pull-request attribution. |
| `metrora models` | Per-model token, cost, task or agent breakdown. |
| `metrora spend` | Machine-readable model-to-project spend flow. |
| `metrora export` | CSV or JSON export. |

Examples:

```bash
metrora overview --provider codex
metrora sessions --period 30days
metrora models --by-task --format markdown
metrora export --format json --from 2026-08-01 --to 2026-08-05
```

## Analysis and diagnostics

| Command | Purpose |
| --- | --- |
| `metrora compare` | Compare observed model performance and efficiency. |
| `metrora optimize` | Find waste and optionally apply reversible configuration fixes. |
| `metrora audit` | Compare provider token evidence with displayed totals and pricing derivation. |
| `metrora doctor` | Diagnose provider discovery paths, session counts and parse health. |
| `metrora yield` | Experimental correlation between AI sessions and Git delivery outcomes. |
| `metrora context` | Experimental session context composition analysis. |
| `metrora codex-tps` | Retrospective Codex generated-token throughput estimate from rollout checkpoints. |

Examples:

```bash
metrora doctor --provider zed
metrora audit --provider codex --format json
metrora compare --provider claude
metrora optimize --apply --dry-run
```

Experimental commands label heuristic or incomplete methodology explicitly. Their output should not be presented as stronger evidence than the source permits.

## Cost and plan configuration

| Command | Purpose |
| --- | --- |
| `metrora budget` | Configure daily, weekly or monthly spend budgets and check them in automation. |
| `metrora plan` | Configure subscription plans and inspect projected usage or overage. |
| `metrora currency` | Select the display currency. |
| `metrora model-alias` | Map a provider model identifier to a canonical pricing identifier. |
| `metrora price-override` | Configure explicit local pricing rates. |
| `metrora model-savings` | Compare a zero-cost local model with a selected paid baseline. |
| `metrora proxy-path` | Mark a project path as subscription-covered while retaining API-equivalent valuation. |

Pricing overrides and aliases affect interpretation of local reports. Preserve exact provider evidence and review configuration changes before relying on them for financial decisions.

## Reversible actions and guardrails

| Command group | Purpose |
| --- | --- |
| `metrora act` | Inspect, report and undo journaled configuration changes. |
| `metrora guard` | Install or manage opt-in session budget guardrails where supported. |
| `metrora sync` | Manage supported local synchronization behavior. |

Use each group’s `--help` output for the available subcommands. Configuration-changing actions should be tested with dry-run or status commands where provided.

## Local device connections

| Command | Purpose |
| --- | --- |
| `metrora share` | Share this device’s structured usage with explicitly paired devices on the local network. |
| `metrora devices` | Discover, pair, remove and summarize local peers. |
| `metrora identity` | Show the public device identity used for local pairing. |

Pairing is explicit and revocable. Combined-device reporting is separate from the local source of truth and must not silently corrupt local history when a peer is unavailable.

## Interfaces and integrations

| Command | Purpose |
| --- | --- |
| `metrora web` | Start the local browser dashboard. |
| `metrora mcp` | Run the local stdio MCP server for supported usage and savings queries. |
| `metrora menubar` | Install the retained macOS menubar development surface. |
| `metrora antigravity-hook` | Install or remove supported Antigravity CLI usage capture. |

The macOS menubar and other retained platform surfaces are not official Metrora distributions until their platform-specific release boundary passes.

## Compatibility aliases

Legacy command aliases remain temporary runtime compatibility shims. They exist to preserve scripts, persisted state and integrations during migration.

New documentation, scripts and releases should use `metrora`. Compatibility aliases may be removed only through an explicit migration that protects existing user-owned state.

Internal paths, versioned schemas and persisted identifiers can still contain historical compatibility names where migration safety requires them. Canonical CLI help, diagnostics and examples use Metrora.
